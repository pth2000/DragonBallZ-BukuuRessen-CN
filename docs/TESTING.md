# 测试规范

发布验证由自动化检查、模拟器测试和真实硬件测试组成。自动化检查用于证明构建结果符合结构约束；人工测试用于确认译文、视觉效果和运行流程。

## 自动化检查

构建器自动验证：

- 源 ROM 和字库基线的 SHA-256；
- LZ10 与 RLE 压缩往返；
- 脚本事件 ID、opcode 和文本字节预算；
- 资源包解压尺寸与 NDS FAT 范围；
- 界面像素修改范围和资源回读；
- BPS 应用往返及目标 ROM 哈希。

提交前运行与 CI 一致的检查：

```powershell
uvx ruff check src tools tests
uv run python -m unittest discover -s tests -v
uv run python tools/check_public_tree.py
uv run python tools/check_release_metadata.py
uv run python tools/check_glossary.py
```

## 工具链回归

修改资源解析、构建器或字形分配逻辑后，还应验证以下流程。

### 提取一致性

对源 ROM 运行 `tools/extract_all.py`。结果应包含 96 个资源包条目和六种语言共 18,312 条文本：

```text
jp 3,100 / en 3,046 / fr 3,041 / ge 3,043 / it 3,042 / sp 3,040
```

数量不一致表示资源包解析或语言分组发生回归。

### 新字形分配

测试用例应覆盖完整链路：

```text
检测缺字 → 分配候选槽 → 写入 0/1 点阵 → 重压缩字库
         → 更新剧情编码 → 生成 ROM/BPS → 回放 BPS
```

自动化检查只能确认槽位符合已知规则，不能证明该槽在所有隐藏界面中均未使用。新增槽位仍需游戏内验证，详见[字库工作流](tech/FONTS.md)。

### 界面阶段

运行 `tools/verify_stages.py`，确认各界面阶段的 ROM、资源、报告和预览与已知基线一致。界面构建器的公共断言见[图片界面](tech/ui/README.md#重绘约束)。

## 自动化与人工验证边界

| 自动化保证 | 人工确认 |
| --- | --- |
| 哈希、压缩往返和 BPS 回放 | 模拟器与实机显示 |
| 文本容量和脚本定位 | 断行、字距和基线观感 |
| 像素修改范围和逐像素回读 | 译文语气与术语一致性 |
| 资源包结构和 FAT 范围 | 长时间运行稳定性 |

所有自动化检查通过并不等同于完成发布验证。

## 模拟器验证

优先使用 melonDS，并按以下方式执行：

1. 更换 ROM 后完全关闭并重新启动模拟器。
2. 不加载旧版本创建的 Save State。
3. 普通 `.sav` 可以复用；出现异常时使用新存档复测。
4. 关闭图像滤镜，并以整数倍缩放检查像素。
5. 分别测试软件渲染和硬件渲染。

## 文本变更检查单

- 新增字形至少在游戏中出现一次。
- 覆盖黑底白字旁白、白底黑字对白和人名栏。
- 检查逗号、句号、问号、省略号及新增标点。
- 检查多行文本、文本框末行和分页。
- 测试正常推进、快速推进和 SKIP。
- 验证修改段落之后的事件、战斗加载和战斗返回流程。

## 路线测试记录

建议为每条路线记录：

```text
角色路线
剧情块 / event ID
正常推进 / SKIP
战斗进入 / 战斗返回
存档 / 读档
缺字 / 重叠 / 断行
译文与术语问题
测试环境与备注
```

## 字形检查

- 整体基线是否上浮或下沉；
- 笔画是否触及左右边界；
- 复杂字是否出现黑块或断笔；
- `口、日、目` 等框形是否闭合；
- `，。！？` 的位置与风格是否一致；
- 相邻字符和上下行是否发生粘连。

## 真实硬件验证

正式发布前至少验证：

- 一台 DS、DS Lite、DSi 或兼容烧录卡；
- 新游戏、普通存档和读档；
- 休眠与唤醒；
- 长时间剧情和战斗切换；
- 至少一条完整路线或对应维护范围。
